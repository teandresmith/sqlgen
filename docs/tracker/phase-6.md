## 6.3c Context Alignment with PRD Section 9.8 — Fix input classification, operations, and filter context

**PRD Reference:** Sections 9.8 (Design Principle 1 — always-generated operations), 10.3 (CreateInput classification — UUID PKs omittable, update_columns/soft delete omittable for backfilling), 11.1 (filter struct — soft delete comparator, no IncludeDeleted), 9.8 (method-level soft delete scoping via `exclude_deleted`)

**Status:** Complete

### Tasks

#### CreateInput classification fixes (`context_table.go:buildCreateInputFields`)

- [x] UUID PKs (strategy `db` or `app`) → `omittable.Value[T]` instead of excluded. Only auto-increment/serial/identity PKs remain excluded. Requires checking whether the PK column is UUID vs auto-increment before deciding to skip.
- [x] `update_columns` (e.g., `updated_at`) → `omittable.Value[T]` instead of excluded. Supports data backfilling where the caller wants to set a specific timestamp.
- [x] Soft delete columns → explicitly `omittable.Value[T]` (currently handled implicitly via nullable path, but should be explicit for clarity and to ensure they're never accidentally excluded).

#### UpdateInput classification fixes (`context_table.go:buildUpdateInputFields`)

- [x] `update_columns` → `omittable.Value[T]` instead of excluded. Same backfilling rationale as CreateInput.
- [x] Soft delete columns → explicitly included as `omittable.Value[T]` (allows manual soft delete management via Update instead of only through SoftDelete/Restore methods).

#### Always-enabled operations (`context_table.go:toResolvedOperations`)

- [x] Force `Get`, `GetMany`, and `Count` to `true` regardless of config values. These are foundational operations: write methods use `Get` for the return path, `Paginate` delegates to `Count` + `GetMany`, and relationship loading uses `GetMany`.

#### New context fields

- [x] Add `ExcludeDeleted bool` to `TableContext` — indicates whether methods should inject default "is not deleted" conditions. Default `true` when `SoftDelete != nil`. Driven by a new `exclude_deleted` config field on `GenerationConfig` (default: not set → auto-detect from soft delete presence).
- [x] Add `IsSoftDeleteColumn bool` to `FilterFieldContext` — marks which filter field corresponds to the soft delete column, so templates can check whether the caller overrode it.
- [x] Add `JSONTag string` to `InputFieldContext` — all generated structs (including Create/Update inputs) carry `json` tags matching the database column name per PRD tag convention.
- [x] Add `exclude_deleted` field to `config.GenerationConfig` (optional `*bool` — `nil` means auto-detect, `true` forces on, `false` forces off).

### Acceptance Criteria

- UUID PK columns (strategy `db`/`app`) appear as `omittable.Value[T]` in CreateInputFields, not excluded
- Auto-increment/serial/identity PK columns remain excluded from CreateInputFields
- `update_columns` appear as `omittable.Value[T]` in both CreateInputFields and UpdateInputFields
- `Get`, `GetMany`, `Count` are always `true` in ResolvedOperations regardless of config input

## 6.4r View Parsing — Annotation files, introspection, and graceful DDL handling

**PRD Reference:** Sections 16.1, 16.2, 16.3

**Status:** Complete

**Blocks:** 6.4s (View Templates)

### Design

Views are populated through two paths, using separate config fields:

1. **Introspection (live DB):** Views are discovered automatically from the database catalog with accurate column names and types. Annotations from `input.views` can overlay to add `@pk`, override types, or force nullability.
2. **Annotation files (`input.views`):** User writes a dedicated `.sql` file containing a `CREATE VIEW` statement with annotation comments (`@pk`, `@type`, `@nullable`). View name is extracted from the `CREATE VIEW` statement. Column type resolution follows PRD 16.3: annotation → schema matching → aggregate inference → `any` fallback. Files are valid, executable SQL.

The two pipelines are separate: `input.paths` handles DDL (tables, enums, types), `input.views` handles view annotation files. `CREATE VIEW` statements in `input.paths` (DDL/migration files) are **skipped gracefully** (no error, no view entry, warning emitted).
